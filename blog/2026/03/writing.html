September

Alpine dtc package failure → Octal Notation in printf

OSH Bug: Reducing dtc package test failure to a printf '%b' bug (aolsen.ca) by Aidan Olsen

Aidan kicked off the grant by going through all the steps to fix an OSH compatibility bug, from end-to-end:

  1. Start from a disagreement in regtest/aports, and reproduce it on a dev machine.
  2. Reduce the bug to a small, failing test case.
    • As you can see from his post, this can be hard. You often need multiple strategies, approaches, and a bit of luck.
  3. Fix the code in OSH interpreter — the printf builtin in this case. (He fixed the bug, though it's not described in the post.)

The underlying issue is that we shared a lexer between echo -e and printf %b. This seems logical, since they both accept similar backslash escapes:

bash$ printf '%b\n' '\0141'  # 0141 is octal for ASCII a
a

bash$ echo -e '\0141'
a

But printf %b doesn't require the leading zero, while echo -e does:

bash$ printf '%b\n' '\141'  # \141 is like \0141
a

bash$ echo -e '\141'        # Nope!
\141

Yes, we are really into the weeds of shell here, but this difference matters for running real shell scripts, like building the dtc package in Alpine Linux.

For many of these bugs, I kept notes on Zulip:

  • #bug-post-mortem > dtc package - printf %b supports \123 as well as \0123

Here's a note I wrote in the spec tests:

- echo -e
  - NO  3 digit octal  - echo -e '\141' does not work
  - YES 4 digit octal
- printf %b
  - YES 3 digit octal
  - YES 4 digit octal
- printf string (outer)
  - YES 3 digit octal
  - NO  4 digit octal
- $'' and $PS1
  - YES 3 digit octal
  - NO  4 digit octal

That is, bash is inconsistent about octal escape notation: in different situations, it can't decide whether it's \0141 only, \141 only, or both!

After digging through these notes, I reminded myself that Gabe also ended up fixing this one: aab8f95. As with the Oily Pine experience and Samuel's work, I noticed that reducing bugs is a lot of work, AND fixing bugs is a lot of work.

That is, it's often effective for 2 different people to work on the same bug, with different mindsets. And not just that: reviewing code is a lot of work, and that's bottlenecked on me, unfortunately. So that's one reason for A Pause in the Project (the blog post before this one).

Fixing \" in Here Docs

Patch Parsers Properly (gebdev.net) by Gabe

In this post, Gabe wrote about a few different strategies for fixing the \" here doc bug that Bram found.

Thank you for making multiple iterations on this change! (And sorry for my confusion in the initial review of this blog post.)

Before the fix, Oils had these tokens IDs, making a distinction:

  • Lit_Chars - for unquoted literals like foo.txt
  • Lit_EscapedChar - for escaped operators like \( and \\ (and maybe more)

To fix this bug, we added Lit_BackslashDoubleQuote. This name is purposely vague, because:

  • \" is an escaped char within double-quoted strings; it means "
  • \" is not an escaped char in here docs; it means \"

(Aside from \", double-quoted strings and here docs have the same escape (\) and subst ($) rules. This is because " terminates a string, but something like EOF terminates a here doc.)

I call the Lit_BackslashDoubleQuote strategy pre-structuring. Inside the lexer, we do enough work to create an "ambiguous" token that is resolved later, inside different parts of the parser.

  • #blog-ideas > Pre-Structuring in the Lexer

Each parser has more knowledge about what it's recognizing, e.g. a string literal or a here doc. In contrast, all of Oils shares the same big modal lexer.

Fixing and enhancing the trap builtin

Implementing trap (daveads.github.io) by Daveads

On Zulip, rolfan-ish noted that

  • trap '' FOO is a special case that registers SIG_IGN (ignore) with the given signal. This is technically different than ...
  • trap ' ' FOO (note the space), which registers a handler with no source code.

Daveads fixed this bug, and also discusses how we use algebraic data types to make this distinction clear.

We want YSH to be a more readable language, so he also added trap --ignore, which is consistent with trap --add and trap --remove.

As mentioned in the last blog post, I landed a few commits to trap after fixes from multiple people. We continually up the code, which often enables upgrading OSH to YSH:

  • #blog-ideas > Lessons From Improving the Trap Builtin
